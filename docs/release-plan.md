## Precedence and dependency rules

The former single final go-live after strict S01–S20 completion is superseded. Stage numbers identify reusable build instructions, not a requirement to finish all lower-numbered modules before an included later portion. All original final functions/business rules and technical/evidence requirements remain. Pull necessary dependencies into each release; do not omit an enabled feature's controls because its full module is later.

Default: **R1 → R2 → R3 → R4**. R3/R4 can exchange order only while commissioning details are pending AND the documented current/manual evidence process supports R4. Ben must approve the revised dependency plan in writing. No swap approved; no dates or delivery estimates invented. Development may continue in separate test environments while an earlier approved release is live.

Each release comprises a separately quoted/estimated build milestone plus **R?-S18 acceptance → R?-S19 migration/training → Ben go-live approval → R?-S20 controlled pilot → Ben expansion acceptance**. The developer must supply milestone effort/cost/date estimates after discovery; these are **BLOCKED — INPUT REQUIRED** from the developer with Ben's priority/resource decisions. Stage readiness is not release approval.

## Ownership and coexistence

Maintain [release ownership/modes](../integration-inventory/release-ownership-modes.csv) with per-function job scope and versions, plus the current-producer inventory. Its rows are planning templates, not active configuration or verified live states. Modes must later be processor-enforced. Separate current route (which can have existing automation) from the new system's Manual mode: Tanya's manual task may verify an invoice produced by an existing Zap.

Every manual action requires Job ID/package, owner, due date, revision, external reference and completion evidence; Waiting requires next follow-up. Sent/received/accepted/confirmed are distinct. Changes create current-revision actions; external update stays pending until verified and old acknowledgements cannot satisfy it. Deduplicate manual tasks. At transfer, reconcile state/IDs and adopt prior work; finish tasks with evidence or supersede with replacement-action links.

For enrolled jobs the new job record owns agreed installation dates; non-pilot jobs retain their planning route. Existing producers must receive one agreed source event: new intake must not replay their triggers. If an old Zap cannot reliably exclude migrated jobs, keep that function manual or rehearse one whole-function cutover. No two creators for the same scope. Preserve IDs/history/open work across live schema extensions while development remains isolated.
